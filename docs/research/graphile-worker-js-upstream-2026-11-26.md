## Remaining coverage and compatibility

1. Rust's calendar conjunction, typed weekday step offsets and non-object
   cron payloads remain as documented in ADR 0007. The upstream OR rule can
   add executions to an existing schedule. Adopting it for existing schedules
   requires a separately versioned compatibility choice and explicit payload
   envelope contract. Predicates let individual callers opt in to their own
   matches.
2. Rust supplies phase callbacks but does not expose the Node middleware
   continuation that can skip the migrator or mutate compiled plugin state.
   Its pinned executor requires a direct or session-mode connection. Custom
   drivers opt in by implementing the session contract described in ADR 0008.
3. The prior locked-array/retirement and batch-loop proposals remain open.
   Rust has no cross-runtime advisory lock identity agreement. Proving mixed
   producer and retirement behavior requires a shared lock/ownership design
   and a two-runtime fixture that covers partial outcomes, shutdown and stale
   recovery. Existing pre-22 rows lack reliable retirement history. Marker
   backfill still requires reliable historical evidence or explicit operator
   selection.
4. Driver reconnect policy and cron/worker failure handling differ by design.
   Native listener reconnection has its own cap and reset behavior. SQLx
   handles transient reconnects and polling remains available after a
   terminal listener error. Initial subscription and worker error Results
   remain visible. Rust's one-shot run and admin CLI remain separate
   entrypoints. No external Prisma endpoint, Cloud SQL Proxy, every host OS
   or arbitrary mixed-runtime schema was exercised.
5. The previously withdrawn braces advisory still supplies no active upstream
   fix to port. No advisory-specific dependency overrides were introduced.
   The optional capability/allowlist product decision in ADR 0004 is
   independent of upstream inspection.

There are no skipped first-parent ranges on upstream main. The compatibility
items above and the proposal ledger describe the remaining boundaries. An
inspected commit does not certify every historical deployment configuration.

  uses the callback backend and can see a temporary table created before
  bootstrap. A forced revision-2 error proves rollback removed the failed
  transaction's writes and that a later run resumes after revision 1.
  Cancellation releases a held advisory lock and allows a subsequent migrate.
  The tests exercise worker initialization, the migration crate, and WorkerUtils
  on an already-current schema. Existing fresh, revision-13, and both
  revision-20 fixtures cover upgrade paths and preserve queued work.

  the same success and injected-failure scenarios in separate UUID databases
  on PostgreSQL 18.7. The successful Node run recorded all 20 revisions on
  one backend. The failed run emitted `migrationError` for SQLSTATE P0001
  after rollback, saw exactly the committed revision-1 row in the same

  and observes the same phases/rollback. A first Node attempt used the event

  fixture passes `(compiledOptions, event)` as required by the actual plugin
  dispatcher. Neither runtime was tested against the other's newly managed SQL
  through a live production database.

## Review follow-up on PR #588

The initial head `63c83d3ef94d4ec417cad4d00212ede98f08ae90`
passed Check, Test (PostgreSQL 14–18 and both TLS protocols), Coverage
(the four driver configurations), and Docs. Codecov patch coverage was
95.0% against the 97.5% target. CodeRabbit's review requested changes.

The CLI regression now copies URL password overrides and TLS certificate
settings to the child using SQLx's option ordering. The cancellation
regression holds a dedicated observer connection before requesting the
migration lock, so it cannot pass by taking the lock again on the same
backend. The deployment guide now explains that worker startup uses the
worker's own connection for migrations and callbacks, including for
polling-only workers.

Additional regressions check both CLI connection configuration errors,
unsupported pinned sessions on custom drivers, and loss of the migration
backend during a revision. The backend-loss fixture verifies that the
failure callback is withheld when rollback cannot be acknowledged, the
pending revision leaves no ledger row, and migration can restart on a
new session.

The follow-up passed `just lint`, `just test-docker` (573 passed, seven
existing ignores), and mdBook. All four migration callback regressions
passed with SQLx on PostgreSQL 12.22, and with both tokio-postgres/rustls
and SQLx/async-std on PostgreSQL 18.7. A TLS-only PostgreSQL 16 fixture
confirmed the CLI fallback preserves the effective URL password and
private CA with `sslmode=verify-full`; the fixture supplied the wrong
password in userinfo to verify that the query value takes precedence.
The initial head also passed local checks for OpenTelemetry 0.30–0.32
and the TLS Docker suites for both protocols.
